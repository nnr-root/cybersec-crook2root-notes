# 📱 Smishing, QR & Collaboration-Platform Testing

> [!abstract] Note of [[Phishing & Messaging Security Testing]]
> Twenty years of anti-phishing engineering was built into one channel. Every message that arrives somewhere else inherits none of it. This note covers what each alternative channel removes — sender provenance, destination visibility, inspection, labelling, reporting — how to test the same scenario across channels to expose the asymmetry, and why revoking a malicious invitation is a different operation from deleting the message that carried it.

## Parent Learning Order
Phishing & Spear-Phishing Methodology -> Smishing, QR & Collaboration-Platform Testing

## Each Channel Removes a Different Defence

> *Your mail gateway rewrites every URL and detonates every attachment. A member of staff scans a QR code from a poster in the Meridian lobby. What did the gateway inspect?*
>
> Hold your answer — the section below is the response.

Nothing. The gateway was never in the path. The message travelled on paper, the destination resolved on a personal phone over a mobile network, and the first enterprise system with any visibility is whatever the phone eventually authenticated against — by which point the decision has already been made.

That is the general shape of the problem. The defences an organisation trusts are concentrated in email, and each alternative channel drops a different subset of them.

| Channel | Sender provenance | Destination visible before commitment | Content inspection | External-party label | Reporting path |
| --- | --- | --- | --- | --- | --- |
| Email | SPF/DKIM/DMARC | Yes, on hover; rewritten by safe links | Gateway + detonation | Standard banner | One-click button |
| SMS | Display name is unauthenticated; sender ID spoofable | Shortened, effectively hidden | None | None | Usually undefined |
| QR code | Physical context only | No — opaque until after the scan | None | None | Rarely exists |
| Team chat | Platform identity, but external tenants federate in | Rich preview, generated by the platform | Varies; often link-only | Present on some platforms | Built-in report action |
| File-share invite | Genuine platform sender | The invite is real; the *file* is the payload | Rarely applied to the invitation | Inconsistent | Often absent |

**The deliberate break:** a QR code is treated as a link in a different costume — same destination, same risk, nothing new to think about.

Three properties make it a materially worse carrier. **The destination is unreadable before commitment**: a human cannot inspect a QR code the way they can hover a hyperlink, so the decision to trust is made before the domain is ever seen. **It moves the interaction to a second device**, typically a personal phone outside MDM, outside the proxy, outside the corporate DNS resolver — the endpoint controls the organisation paid for are all on the wrong machine. And **the trust cue is physical**: a sticker on a legitimate poster, a laminated card on a meeting-room table, an overlay on a car-park sign inherits the credibility of the building it is standing in, which no email header ever gets to borrow.

**How you'd spot it:** at the destination, not the code. The URL that opens is a normal URL — check that the domain is one you would have accepted in an email, that it is not a shortener hiding the real host, and that a login page reached this way is one you navigated to yourself rather than one that was handed to you. In the environment, the tell is a QR code physically applied over or beside existing signage: legitimate printed codes are part of the artwork, not stuck on top of it.

## When the Domain Is Not the Domain It Renders As

Destination inspection also fails when the domain *is* visible but reads as something else. Internationalised domain names allow non-ASCII characters, which the browser encodes into an ASCII form beginning `xn--`.

```bash
python3 -c "
s = 'xn--pple-43d.com'.encode().decode('idna')
print(s, [hex(ord(c)) for c in s[:2]])
"
```

Expected output:

```text
аpple.com ['0x430', '0x70']
```

The first character is `U+0430`, CYRILLIC SMALL LETTER A — not the Latin `a` at `U+0061`. On a screen the two are the same glyph, so the label reads as Apple to any human and resolves somewhere else entirely. Visual inspection cannot win this; the difference exists only in the codepoint.

Two defences apply, and the second is the one that scales. Browsers refuse to render the Unicode form when a label **mixes scripts**, displaying the raw `xn--` form instead — which is why an address bar showing `xn--` is always worth a second look. And an organisation that publishes its real domains as a managed allow-list moves the judgement off the person entirely, since `meridian.test` either matches the list or it does not.

## The Collaboration Platform Inherits Trust It Did Not Earn

Chat and file-sharing platforms carry an assumption that everyone present belongs — the roster is the authentication. External federation breaks that assumption quietly.

An external tenant that is permitted to message into Meridian's workspace arrives with a display name it chose, in the same interface as colleagues, with the platform's own visual chrome around it. The message is genuinely from the platform, so nothing about its delivery is anomalous. Where the platform shows an "external" tag, it is small, and where federation is permitted by default, no tag appears at all.

Two attack shapes matter here beyond the link:

- **Application consent.** An OAuth application requesting access to files or mail arrives through the platform's real consent flow. A user who approves it grants a token that continues to work after any message is deleted, after a password change, and often after a session revocation.
- **The invitation itself as payload.** A file-share invitation is legitimately sent by the platform's own infrastructure, passing every authentication check, with the hostile content one click away in a document that no mail gateway ever saw.

> [!tip] The analogy, and where it breaks
> A federated chat workspace behaves like an office with an unstaffed side door: everyone inside is assumed to have come through reception. The analogy breaks in the direction that matters for response — an unauthorised visitor can be escorted out, whereas a granted OAuth token has already left with a copy of the keys. Removing the person does not remove the access.

## Testing the Same Scenario Across Channels

The design that exposes control asymmetry holds the scenario constant and varies only the channel. One harmless business pretext, one canary destination, three deliveries.

```text
Exercise:       SE-TEST-142
Scenario:       "confirm your details for the depot rota change"
Canary:         landing page records an opaque exercise ID only —
                no credentials, no device fingerprinting beyond the metric
Delivery A:     email from a controlled domain
Delivery B:     SMS from a company-owned number
Delivery C:     collaboration invite from a controlled external tenant
Measured:       delivered? · labelled external? · inspected? ·
                reported? · by what route? · visible to the SOC?
Infrastructure: company-owned number and tenant — never a personal account
```

The finding is almost always the same shape and it is the point of running it: the message blocked and labelled in email arrives clean over SMS, and the SOC has no telemetry for it at all. That comparison is far more actionable than any single channel's numbers, because it names a specific missing control rather than a rate.

## Remediation Is Revocation, Not Deletion

The response most organisations rehearse is deleting the message. For these channels that is insufficient in a specific and testable way, so test the revocation path explicitly:

- **Withdraw the invitation and the sharing grant**, not only the notification — a shared link usually survives the deletion of the message that announced it.
- **Revoke the application grant and its refresh tokens**, and confirm the token stops working rather than assuming it does.
- **Restrict external tenants** to an allow-list, so federation is a decision rather than a default.
- **Extend safe-link inspection and external labelling** to chat, where the platform supports it.
- **Give SMS and QR a reporting route** — a monitored number, a service-desk path — because a channel with no way to report is a channel with no detection.
- **Correlate across mail, mobile, identity and collaboration logs**, since a campaign run across channels is invisible to any single one of them.

## Summary

You should now be able to:

- Explain what each alternative channel removes relative to email — sender provenance, destination visibility, inspection, labelling, reporting — and why a QR code is a materially worse carrier than a hyperlink rather than an equivalent one.
- Decode a punycode domain to its rendered form, explain why homograph labels defeat visual inspection, and name the browser behaviour and the organisational control that address it.
- Describe how external federation and application consent let a collaboration platform lend trust it did not earn, and why a granted token outlives the message that requested it.
- Design a cross-channel comparison using one scenario and a canary destination, and specify a remediation that revokes access rather than deleting messages.
